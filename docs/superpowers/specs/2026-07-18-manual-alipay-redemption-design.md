# 人工支付宝审核与邮件兑换码设计

## 目标

个人支付宝收款码不能向本站提供可信的支付回调。本功能让用户完成固定金额的支付宝扫码付款后，仅提交邮箱和“已完成支付”请求；管理员在后台按套餐、金额和提交时间核对自己的支付宝到账记录，确认后由系统将一次性兑换码发送到该邮箱。

不采集付款截图，不接入支付宝开放平台，不自动判断支付成功。

## 用户流程

1. 已登录用户点击 Lite 或 Pro 的升级按钮。
2. 弹窗默认带入账户邮箱；没有邮箱时要求填写有效邮箱。
3. 用户确认后，系统创建一笔 `PENDING` 订单，并显示对应套餐的固定金额和支付宝付款入口。
4. 手机端将“打开支付宝支付 ¥4.99/¥9.99”作为主操作：用户点击后通过付款链接唤起支付宝。电脑端展示同一付款入口对应的二维码，供手机扫码。
5. 用户在支付宝完成付款、返回网页后点击“我已完成支付”。该操作将订单置为 `SUBMITTED`，记录提交时间。
6. 页面提示将在人工核对到账后把兑换码发送到该邮箱；不承诺即时到账。
7. 用户收到邮件后在兑换码入口兑换，会员订阅立即生效。

用户不可通过订单接口更改套餐、金额、邮箱或直接把订单设为已支付。

## 管理员流程

1. 管理员在现有 `/admin` 页面查看 `SUBMITTED` 订单，列表显示订单号、套餐、金额、邮箱、创建/提交时间。
2. 管理员在支付宝收款记录中按金额和时间人工核对。
3. 核对成功后点击“确认并发送兑换码”。服务端在同一事务中创建单次兑换码、将订单标记为 `FULFILLED`，并保存发码时间。
4. 邮件发送失败时订单保持待发送状态，管理员可重试发送；兑换码不会重复创建。
5. 管理员可拒绝明显无效的订单，填写内部备注；用户看到订单未通过而不会得到支付细节。

## 数据与接口

新增 `manual_payment_order`：订单号、用户 ID、邮箱、套餐、固定金额（分）、状态、提交时间、管理员 ID、内部备注、兑换码 ID、创建/更新时间。

新增 `activation_code` 和 `activation_code_redemption`：兑换码仅存哈希，含套餐、月数、有效期、单次使用限制、发放订单及实际兑换用户。兑换时使用既有 `QuotaService.upgradeSubscription`，因此续费会从未过期订阅结束日顺延。

新增已登录用户接口：创建订单、提交已付款、查看自己的订单、兑换码兑换。新增管理员接口：查看订单、确认发码、重试邮件、拒绝订单。所有管理员接口在服务端根据用户角色校验，不依赖前端路由隐藏。

现有公开可调用的 `/quota/upgrade` 不再作为前端升级路径；应移除或限制为管理员内部能力，防止绕过付款直接升级。

## 邮件与配置

后端添加 Spring Mail。SMTP 主机、端口、账号、应用专用密码、发件人地址通过生产环境变量配置，绝不写入仓库。开发环境邮件使用可观察的本地替代实现或明确禁用真实投递。

支付宝付款链接和二维码图片均由部署配置提供：`PAYMENT_ALIPAY_LITE_URL`、`PAYMENT_ALIPAY_PRO_URL`、`PAYMENT_ALIPAY_LITE_QR_URL` 与 `PAYMENT_ALIPAY_PRO_QR_URL`。前端依据设备类型优先显示唤起支付宝按钮或二维码。套餐价格在服务端固定为 Lite 499 分、Pro 999 分，前端只展示服务端返回的订单信息，避免客户端篡改。

邮件包含兑换码、套餐、有效期与兑换入口，不包含支付截图或敏感的支付宝信息。

## 错误处理与约束

- 未登录用户点击升级时先跳转登录。
- 未填写邮箱、邮箱格式不合法、相同用户存在未完成同套餐订单时拒绝创建。
- `PENDING` 订单未提交可重新展示付款码；`SUBMITTED` 订单不可重复提交。
- 管理员确认只能处理 `SUBMITTED` 订单；接口幂等，重复点击不产生额外兑换码。
- 兑换码格式会去除空格和连字符再校验，失效、已用或不存在时返回统一失败提示。
- 邮件投递记录不等同于邮件送达；用户可在已登录订单页查看已发放兑换码，避免邮箱延迟造成无法使用。

## 测试

后端以单元/集成测试覆盖：创建与提交订单、普通用户越权、管理员确认的幂等性、邮件失败重试、兑换码单次使用、过期码与兑换后订阅时长。

前端验证：套餐弹窗的邮箱校验、订单状态显示、管理员确认/重试操作。完成后运行后端 Maven 测试、前端类型检查与生产构建。

## 非目标

- 不自动核验支付宝到账。
- 不上传付款截图。
- 不支持退款自动化、发票或多币种。
- 不替代未来合规商户支付接入；之后接入支付渠道时可复用订单和发货边界。
